# Simple LLM Agent

Минимальное fullstack-приложение: React + TypeScript + Vite на frontend, Node.js + Express + TypeScript на backend.

## Что делает приложение

Пользователь вводит запрос в чат. Backend принимает сообщение, передает его отдельной сущности `SimpleAgent`, агент вызывает LLM через HTTP API и возвращает ответ в интерфейс.

Агент сохраняет историю каждого чата в отдельный JSON-файл внутри `server/data/agent-sessions/`, загружает ее при каждом запуске и отправляет прошлые сообщения выбранного чата в следующий LLM-вызов. Поэтому после перезапуска backend продолжает каждый диалог со своим контекстом.

## Явная модель памяти

Над памятью работает слой персонализации. Профиль пользователя явно задаёт имя, контекст (роль, опыт, сфера и цели), стиль ответа, формат и список постоянных ограничений. Выбранный `profileId` передаётся в каждом `POST /api/agent`, а сервер сам загружает профиль и добавляет его в защищённый system-контекст. Этот контекст применяется автоматически и не отключается вместе с долговременной памятью.

Профили хранятся в `server/data/profiles/<profileId>.json`. Долговременная память тоже изолирована по `profileId`, поэтому автоматически выученные предпочтения не смешиваются между людьми.

Память разделена физически и логически на три слоя:

| Слой | Что хранится | Область действия | Хранилище | Запись |
|---|---|---|---|---|
| Краткосрочная | сообщения текущего диалога | один чат | `server/data/agent-sessions/<sessionId>.json` | автоматически после успешного ответа |
| Рабочая | сжатое состояние всей задачи: цель, прогресс, ограничения, решения, артефакты и следующие шаги | одна задача/чат | `server/data/memory/working/<sessionId>.json` | пересобирается моделью после каждого успешного ответа; ручные записи сохраняются отдельно |
| Долговременная | профиль, решения, знания | профиль пользователя | `server/data/memory/long-term/default.json` | важные сведения профиля — автоматически; решения и знания — после подтверждения или явно через UI/API |

Перед каждым вызовом модели агент собирает prompt в порядке приоритета: system prompt, долговременная память, рабочее сжатие задачи, свежий хвост диалога, затем текущий запрос. В отчёте ответа `contextManagement.memory` видно количество элементов, токены и ID записей, которые действительно попали в prompt. Если окно контекста мало, свежий диалог и основная цель/ограничения рабочей памяти имеют приоритет над долговременной.

После завершения каждого хода отдельный LLM-вызов получает предыдущее рабочее сжатие, свежую историю и новую пару `user/assistant`. Он возвращает строгий JSON с обновлённым состоянием всей задачи и кандидатами в долговременную память. Поэтому working не является копией последних сообщений: старые договорённости остаются в сжатии, пока актуальны, а устаревшие удаляются моделью.

Кандидаты long-term извлекаются из запросов пользователя во всём доступном окне с учётом рабочего сжатия и уже накопленного профиля. Агент формирует короткую выжимку, а не копирует последнюю реплику. Устойчивые и важные сведения категории `profile` (язык, роль, стиль ответа, предпочтения и постоянные ограничения пользователя) сохраняются автоматически в стабильные профильные ключи; повторный сигнал обновляет существующую выжимку вместо создания дубликата. Решения и знания попадают в `pending`, где ждут подтверждения. Низкая уверенность не меняет память, `update/delete` требуют существующий `targetId`, а автоматическое удаление запрещено. Порог уверенности задаётся через `MEMORY_CONFIDENCE_THRESHOLD` (по умолчанию `0.75`), порог автоматического сохранения профиля — через `MEMORY_PROFILE_AUTO_SAVE_THRESHOLD` (по умолчанию `0.7`). Долговременная память хранится в общем `memory/long-term/default.json` и добавляется в контекст любого диалога.

В UI есть независимые переключатели рабочей и долговременной памяти. Они управляют только использованием слоя в ответе: выключенный слой не попадает в prompt, но его данные не удаляются. Рабочее сжатие продолжает обновляться после хода, поэтому можно сравнивать ответы с памятью и без неё, не теряя накопленный контекст. Выбор переключателей сохраняется в браузере.

Значения памяти передаются модели как экранированные данные внутри `<memory_data>`, поэтому сохранённый текст не может закрыть блок и подменить system prompt. При нехватке контекста сначала отбрасывается long-term, затем менее важный working и старая история; цель и ограничения working получают приоритет.

API памяти:

```text
GET    /api/agent/memory?sessionId=<id>
POST   /api/agent/memory
DELETE /api/agent/memory/:layer/:id?sessionId=<id>
GET    /api/agent/memory/pending?sessionId=<id>
POST   /api/agent/memory/pending/:id/approve
POST   /api/agent/memory/pending/:id/reject
```

API профилей:

```text
GET    /api/profiles
POST   /api/profiles
PUT    /api/profiles/:id
DELETE /api/profiles/:id
```

Каждый запрос получает `turnId`. Структурированные шаги `memory_load`, `memory_classification`, `memory_policy`, `context_assembly`, `provider_request`, `conversation_persist` и `memory_persist` сохраняются отдельно от истории в `server/data/agent-logs/<sessionId>/<turnId>.json`.

```text
GET /api/agent/logs?sessionId=<id>
GET /api/agent/logs/:turnId?sessionId=<id>
```

Пример явной записи:

```json
{
  "sessionId": "win-demo",
  "layer": "working",
  "category": "constraint",
  "key": "response_format",
  "value": "Отвечать коротким списком"
}
```

Для проверки изоляции слоёв и их влияния на prompt выполните `npm test`. Интеграционные тесты также создают два контрастных профиля, проверяют разные system-prompt и подтверждают, что профиль применяется даже при выключенной long-term памяти.

Главное требование выполнено: логика запроса, ответа и восстановления контекста инкапсулирована в агенте, а endpoint `/api/agent` только валидирует входные данные, создает агента и запускает его.

Хранилище использует атомарную запись через временный файл, хранит завершенные пары `user`/`assistant` и формирует ограниченное контекстное окно из памяти и свежей истории, чтобы старые диалоги не раздували каждый prompt бесконечно.

Текстовое описание агента лежит отдельно в Markdown-файле:

```text
server/agents/simple-agent.md
```

В этом же файле лежат дефолтные настройки агента: модель, temperature, язык, system prompt и демонстрационные лимиты контекста:

```text
max_context_tokens: 40000
reserved_output_tokens: 500
```

## Модель агента

Агент работает через DeepSeek Flash:

```text
MODEL_FLASH_NAME=deepseek-v4-flash
MODEL_FLASH_BASE_URL=https://api.deepseek.com
```

Вызов выполняется через OpenAI-compatible endpoint:

```text
POST https://api.deepseek.com/chat/completions
```

Перед отправкой сообщения модель можно выбрать в интерфейсе. Список формируется на сервере только из настроенных моделей (`MODEL_GEMINI`, `MODEL_FLASH`, `MODEL_PRO`), а выбранный ID проверяется endpoint-ом `/api/agent`. Выбор сохраняется в браузере и используется как для основного ответа, так и для обновления памяти после хода.

## Настройка

Создайте `.env` в корне проекта:

```bash
cp .env.example .env
```

Заполните ключ:

```bash
DEEPSEEK_API_KEY=your_deepseek_api_key_here
```

Параметры памяти агента можно переопределить через `.env`:

```bash
AGENT_MAX_CONTEXT_MESSAGES=40
AGENT_MAX_CONTEXT_CHARACTERS=24000
AGENT_CONTEXT_KEEP_LAST_MESSAGES=5
MODEL_MAX_CONTEXT_TOKENS=40000
MODEL_RESERVED_OUTPUT_TOKENS=500
```

`AGENT_CONTEXT_KEEP_LAST_MESSAGES` задает N последних сообщений, которые агент подставляет в prompt как есть. Отдельного пользовательского выбора режима контекста нет: агент всегда использует единый порядок `system → long-term → working → свежая история → текущий запрос`.

`AGENT_MAX_CONTEXT_MESSAGES` и `AGENT_MAX_CONTEXT_CHARACTERS` остаются дополнительной защитой для точного хвоста истории. Значения выше всё ещё достаточно маленькие для демонстрации: короткий запрос проходит, длинный диалог показывает рост истории, а большое сообщение может превысить локальный budget. Если в `.env` уже указаны `MODEL_MAX_CONTEXT_TOKENS` или `MODEL_RESERVED_OUTPUT_TOKENS`, они переопределят настройки из файла агента.

Backend также считает токены для текущего запроса, выбранной истории, полной истории диалога и ответа модели. Если API возвращает `usage`, итоговые `input/output/total` берутся из API; если нет, используется локальная оценка. История для следующего вызова собирается из памяти и последних N сообщений, а одиночный запрос больше локального budget отклоняется до обращения к LLM.

После ответа UI показывает сравнение:

- `input без управления`: сколько токенов занял бы prompt с полной историей.
- `managed input`: сколько токенов реально вошло в управляемый prompt.
- `экономия`: разница в токенах и процентах.
- `как есть`: сколько последних сообщений сохранено без изменений.

В интерфейсе есть sidebar со списком чатов в стиле Codex. При старте frontend вызывает `GET /api/agent/chats`; если сохраненные чаты есть, они появляются в списке и выбранный чат загружает свою историю. Новый чат получает свой `sessionId` в URL, например:

```text
http://localhost:5173?sessionId=win-demo-1
```

Для каждого чата UI показывает отдельную статистику: сколько сообщений в истории, сколько токенов занимает история, общий лимит контекста, резерв на ответ, input-лимит, сколько input-токенов уже занято историей, сколько осталось для следующего запроса, сколько стоит повторная отправка истории и есть ли риск переполнения на следующем коротком запросе.

Для демонстрации роста токенов и стоимости также есть endpoint:

```text
GET /api/agent/token-demo
```

Он сравнивает короткий диалог, длинный диалог и диалог выше лимита модели. Основной UI оставлен простым, а endpoint можно использовать отдельно, чтобы показать, как каждый новый ход повторно отправляет историю, почему input-токены и стоимость растут, и что ломается при переполнении контекста.

Что показать при переполнении:

- Если отправить историю целиком, API модели может вернуть ошибку контекстного окна: запрос физически больше лимита модели.
- Если агент защищается и режет историю, старые факты исчезают из prompt: модель может забыть имя пользователя, ранние требования, ограничения задачи или принятые решения.
- Стоимость растет не только от нового сообщения: каждый следующий ход повторно оплачивает выбранную историю диалога.
- Слишком большой одиночный запрос ломается сразу: агент отклоняет его до вызова LLM и сообщает, на сколько токенов превышен лимит.

```bash
npm run dev
```

Frontend будет доступен на `http://localhost:5173`.
Backend будет доступен на `http://localhost:3001`.

```bash
npm run build
npm start
```
