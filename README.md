# Quanta — RAG с query rewrite и реранкингом

Fullstack-приложение на React, TypeScript и Express. Поверх локальной индексации реализован двухэтапный RAG: широкий векторный поиск, query rewrite, эвристический reranker, фильтрация по relevance threshold и финальный `top-K`.

Улучшенный RAG встроен поверх функциональности предыдущих этапов. В приложении сохранены полноценный агент, история чатов, управление контекстом и токенами, рабочая и долгосрочная память, профили, инварианты, состояния задач, Planner, MCP connections и Google Calendar MCP.

## Что реализовано

- Поддержка `.md`, `.mdx`, `.txt`, `.html`, `.json`, `.js`, `.jsx`, `.ts`, `.tsx`, `.css`, `.py` и `.pdf`.
- PDF преобразуется в текст локальной утилитой `pdftotext` (Poppler).
- Фиксированный chunking: окно 1 200 символов, overlap 180 символов.
- Структурный chunking: границы Markdown-заголовков/разделов, максимум 1 800 символов.
- Для каждого чанка сохраняются `source`, `title`, `section`, `chunk_id`, стратегия, текст, число токенов и embedding.
- Автономные 128-мерные эмбеддинги на основе signed feature hashing; внешний API не требуется.
- Индекс атомарно сохраняется в `server/data/index.json`.
- Векторный поиск использует косинусную близость.
- Отдельный экран `#index`: схема процесса, реальные метрики, сравнение стратегий, просмотр чанков и поиск по активной стратегии.
- Параметры chunking, загрузка документов, выбор стратегии и схема процесса спрятаны в компактные раскрывающиеся панели.
- Активная стратегия — рабочая настройка агента: она применяется к обычным сообщениям, прикреплённым документам и поиску по локальному индексу.
- Настройки chunking: фиксированный размер, overlap и максимальный размер структурного раздела.
- Два рабочих режима RAG: baseline и improved. На запрос используется только режим, выбранный в настройках агента.
- Query rewrite выполняется выбранной LLM; при ошибке используется исходный запрос.
- Reranker объединяет cosine similarity, покрытие терминов и совпадения в заголовке/разделе.
- Порог и оба `top-K` настраиваются через `.env`.
- Grounding-контракт требует от модели структурированный ответ с `chunk_id` и дословными цитатами.
- Сервер проверяет, что каждый `chunk_id` действительно был найден, цитата содержится в чанке, а смысл ответа пересекается с цитатами. `source` и `section` сервер подставляет из индекса, а не принимает на веру от модели.
- Пользовательский ответ всегда содержит разделы «Ответ», «Источники» (`source + section + chunk_id`) и «Цитаты».
- Для каждого `sessionId` ведётся отдельная структурированная память задачи: цель, явно уточнённые факты, ограничения, терминология, открытые вопросы и текущий шаг.
- Память задачи сохраняется атомарно в `server/data/task-memory/<sessionId>.json`, ограничена по размеру и восстанавливается независимо от истории. Повреждённый файл получает суффикс `.corrupt-<timestamp>` и заменяется пустым состоянием.
- Перед каждым ответом память обновляется из нового сообщения пользователя, после чего участвует в query rewrite и RAG-поиске. Текущий вопрос повторяется в поисковом представлении и имеет больший вес, чем память.

Синтетический корпус не создаётся. Пока пользователь не загрузил реальные документы, индекс остаётся пустым. Файлы можно добавить на экране «Индексация» или прикрепить непосредственно к сообщению агенту; после загрузки они сохраняются в `server/data/documents` и автоматически индексируются.

При каждом запросе агент самостоятельно ищет релевантные фрагменты в локальном индексе и получает их как защищённый справочный контекст. Если документ прикреплён к сообщению, его фрагменты приоритетно передаются агенту в текущем запросе. Стратегию можно переключить на экране индексации или в отдельном окне настроек агента; выбор сохраняется в браузере и передаётся серверу с каждым запросом.

В режиме baseline запрос сразу отправляется в векторный поиск. В improved запрос сначала переформулируется, затем кандидаты реранжируются, отсекаются по порогу и ограничиваются финальным `top-K`. Если подходящих фрагментов нет, обычные вопросы передаются модели без файлового контекста. Строгий ответ «Не знаю» сохраняется для запросов, которые явно требуют ответа по документам или прикреплённым файлам.

В окне настроек также можно очистить историю текущего чата или удалить все сохранённые диалоги.

Память задачи отображается над перепиской в раскрываемом блоке и очищается отдельно. Удаление чата удаляет одновременно историю, working memory, pending memory, логи и структурированную память задачи. Профиль и long-term memory остаются профильными и не смешиваются с памятью конкретного чата.

Схема памяти:

```ts
type TaskMemoryState = {
  version: 1;
  sessionId: string;
  goal: string | null;
  clarifiedFacts: Array<{ key: string; value: string; sourceMessageId: string }>;
  constraints: Array<{ id: string; value: string; sourceMessageId: string }>;
  terminology: Array<{ term: string; meaning: string; sourceMessageId: string }>;
  openQuestions: string[];
  currentStep: string | null;
  updatedAt: string;
};
```

## Запуск

```bash
npm install
cp .env.example .env
npm run index:aurora
npm run dev
```

Frontend: `http://localhost:5173`. Экран индексации: `http://localhost:5173/#index`.

Для чата можно выбрать DeepSeek или Ollama на другом компьютере. Индексация и поиск выполняются локально. При подключении через интернет Ollama должна быть закрыта шлюзом с API-ключом; готовая конфигурация находится в [`gateway/README.md`](gateway/README.md).

### Подключение Ollama внутри локальной сети

На Windows-компьютере с Ollama разрешите подключения из локальной сети и перезапустите приложение Ollama:

```powershell
[Environment]::SetEnvironmentVariable('OLLAMA_HOST', '0.0.0.0:11434', 'User')
```

Разрешите входящие TCP-подключения к порту `11434` в брандмауэре только для частной сети. Узнайте IPv4-адрес командой:

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -notlike '127.*' } | Select-Object InterfaceAlias, IPAddress
```

Для подключения только внутри доверенной локальной сети на компьютере с этим проектом добавьте в `.env`:

```dotenv
AGENT_MODEL_ID=local
MODEL_LOCAL_TITLE=Локальная: Qwen 3.5 9B
MODEL_LOCAL_BASE_URL=http://192.168.1.50:11434/v1
MODEL_LOCAL_NAME=qwen3.5:9b
MODEL_LOCAL_INPUT_PRICE_PER_1M=0
MODEL_LOCAL_OUTPUT_PRICE_PER_1M=0
MODEL_LOCAL_MAX_CONTEXT_TOKENS=8192
MODEL_LOCAL_RESERVED_OUTPUT_TOKENS=600
MODEL_LOCAL_TEMPERATURE=0.1
MODEL_LOCAL_CONTEXT_WINDOW=8192
MODEL_LOCAL_MAX_OUTPUT_TOKENS=600
MODEL_LOCAL_TOP_P=0.9
MODEL_LOCAL_SEED=42
```

Замените `192.168.1.50` на адрес Windows-компьютера. Не пробрасывайте порт `11434` в интернет. Для работы через разные сети используйте защищённый HTTPS-шлюз из [`gateway/README.md`](gateway/README.md), а не этот LAN-вариант. После запуска проекта проверьте соединение:

```bash
curl http://localhost:3001/api/ollama/status
```

Ответ должен содержать `"online":true` и `"modelAvailable":true`. В настройках агента появятся обе модели: локальная Ollama и DeepSeek.

`MODEL_LOCAL_MAX_CONTEXT_TOKENS` задаёт бюджет контекста на стороне агента. `MODEL_LOCAL_CONTEXT_WINDOW` передаётся самой Ollama как `num_ctx`, а `MODEL_LOCAL_MAX_OUTPUT_TOKENS` — как `num_predict`. Локальная модель вызывается через нативный `/api/chat`, поэтому приложение получает фактическое число токенов и длительности генерации от Ollama.

### Benchmark и квантование локальной модели

Для сравнения одной модели до и после оптимизации задайте два профиля. Теги должны уже существовать в Ollama; доступные варианты проверьте командой `ollama list` на компьютере с моделью:

```dotenv
MODEL_LOCAL_BASELINE_NAME=qwen3.5:9b
MODEL_LOCAL_BASELINE_TEMPERATURE=0.2
# num_ctx, num_predict, top_p и seed не задаются:
# профиль «до» воспроизводит прежние настройки Ollama по умолчанию.

MODEL_LOCAL_OPTIMIZED_NAME=qwen3.5:9b
MODEL_LOCAL_OPTIMIZED_TEMPERATURE=0.1
MODEL_LOCAL_OPTIMIZED_CONTEXT_WINDOW=8192
MODEL_LOCAL_OPTIMIZED_MAX_OUTPUT_TOKENS=600
MODEL_LOCAL_OPTIMIZED_TOP_P=0.9
MODEL_LOCAL_OPTIMIZED_SEED=42
LOCAL_LLM_BENCHMARK_REPETITIONS=3
```

Чтобы измерить эффект квантования, укажите в `MODEL_LOCAL_BASELINE_NAME` и `MODEL_LOCAL_OPTIMIZED_NAME` разные установленные теги одной модели. Конкретные имена зависят от опубликованных вариантов модели; benchmark прочитает реальный `quantization_level` через Ollama `/api/show`, не пытаясь определить его по имени.

Запуск:

```bash
npm run evaluate:local-llm
```

Команда сравнивает исходный вариант (старый общий prompt, `temperature=0.2`, остальные параметры генерации по умолчанию Ollama) с оптимизированным вариантом (специализированный RAG-prompt, `temperature=0.1`, `num_ctx=8192`, `num_predict=600`, `top_p=0.9`, фиксированный seed). Каждый профиль прогревается, затем трижды выполняет 11 контрольных вопросов корпуса «Аврора». Отчёты сохраняются в `server/data/benchmarks/local-llm-latest.md` и `.json` и содержат общие показатели и качество по каждому вопросу, median/p95, токены в секунду, размер модели и VRAM из `/api/ps`. Допустимый порог — потеря качества не более 3 процентных пунктов.

`npm run index:aurora` копирует четыре подготовленных документа из `rag-test-data` в локальное хранилище и строит индекс. Контрольные вопросы и ожидаемые ответы находятся в `rag-test-data/control-questions.md`.

Настройки retrieval в `.env`:

```dotenv
RAG_SEARCH_TOP_K=8
RAG_FILTERED_TOP_K=3
RAG_RELEVANCE_THRESHOLD=0.22
```

Основные разделы доступны через новую навигацию: «Ассистент», «Планировщик», «MCP» и «Индексация». Для Google Calendar и дополнительных моделей используйте переменные из `.env.example`.

## Проверка на корпусе «Аврора»

1. Выполните `npm run index:aurora`, затем `npm run dev`.
2. В настройках агента включите RAG, выключите рабочую и долговременную память и выберите нужный режим.
3. Задайте контрольный вопрос и сверьте ответ и источники с таблицей `rag-test-data/control-questions.md`.
4. Раскройте диагностику под ответом: там видны rewrite, документы после threshold, relevance score и средняя релевантность только выбранного режима.

Строгий отрицательный тест — «Согласно загруженным документам, где находится московский офис проекта „Аврора“?». Ни один фрагмент не должен пройти порог, поэтому ответ обязан перейти в режим «Не знаю». Без явной ссылки на документы вопрос будет передан самой модели.

Тест `grounded-answer.test.ts` прогоняет 10 содержательных вопросов и для каждого автоматически проверяет наличие источников, наличие точных цитат и смысловое соответствие ответа цитатам. Дополнительные отрицательные проверки подменяют цитату и передают пустой/слабый контекст: оба случая должны завершиться контролируемым «Не знаю».

`task-memory-scenarios.test.ts` содержит два детерминированных диалога по 12 сообщений: план промышленного запуска и решение проектного комитета по бюджету/эксплуатации. Mock LLM обновляет память без сети; тесты проверяют сохранение цели, разрешение «этого варианта», замену ограничения, терминологию и grounding всех фактических ответов.

## API

- `GET /api/index` — получить индекс; при отсутствии он будет создан.
- `POST /api/index/rebuild` — перечитать документы и перестроить индекс.
- `POST /api/index/search` — поиск, тело: `{ "query": "...", "strategy": "structural" }`.
- `GET /api/documents` — список реальных документов в локальном хранилище.
- `POST /api/documents/upload` — загрузить документ и автоматически обновить индекс.
- `DELETE /api/documents` — удалить все загруженные документы и пересобрать пустой индекс.
- `DELETE /api/documents/:name` — удалить документ и его чанки из индекса.
- `POST /api/agent` — запрос агенту; `retrievalStrategy` принимает `fixed` или `structural`, `ragMode` — `baseline` или `improved`.
- `GET /api/ollama/status` — проверить удалённую Ollama и наличие настроенной модели.
- `GET /api/agent/history?sessionId=...` — восстановить историю вместе с сохранённым grounding каждого ответа.
- `GET /api/agent/task-memory?sessionId=...` — получить структурированную память текущего чата.
- `DELETE /api/agent/task-memory?sessionId=...` — очистить только структурированную память текущего чата.
- `DELETE /api/agent/history?sessionId=...` — очистить текущий диалог и его рабочие данные.
- `DELETE /api/agent/chats` — удалить всю историю диалогов.
- `POST /api/chat` — существующий чат через DeepSeek.

Для больших коллекций JSON-хранилище можно заменить на SQLite или FAISS: контракт чанка и UI останутся прежними.

Ответ `POST /api/agent` дополнительно содержит:

```json
{
  "answer": "Ответ:\n...",
  "grounding": {
    "status": "grounded",
    "sources": [{ "source": "...", "section": "...", "chunkId": "str-...", "relevance": 0.91 }],
    "citations": [{ "chunkId": "str-...", "quote": "дословная цитата" }]
  },
  "taskMemory": { "version": 1, "sessionId": "..." }
}
```

Известные ограничения: извлечение изменений памяти использует настроенную LLM и при её ошибке безопасно сохраняет последнее валидное состояние; эвристическая проверка смыслового пересечения не является полноценной entailment-моделью; локальный hashing-embedding рассчитан на небольшой корпус.
