# Simple LLM Agent

Минимальное fullstack-приложение: React + TypeScript + Vite на frontend, Node.js + Express + TypeScript на backend.

## Что делает приложение

Пользователь вводит запрос в чат. Backend принимает сообщение, передает его отдельной сущности `SimpleAgent`, агент вызывает LLM через HTTP API и возвращает ответ в интерфейс.

Агент сохраняет историю каждого чата в отдельный JSON-файл внутри `server/data/agent-sessions/`, загружает ее при каждом запуске и отправляет прошлые сообщения выбранного чата в следующий LLM-вызов. Поэтому после перезапуска backend продолжает каждый диалог со своим контекстом.

Главное требование выполнено: логика запроса, ответа и восстановления контекста инкапсулирована в агенте, а endpoint `/api/agent` только валидирует входные данные, создает агента и запускает его.

Хранилище использует атомарную запись через временный файл, хранит завершенные пары `user`/`assistant`, хранит summary старых блоков отдельно и формирует отдельное контекстное окно для LLM, чтобы старые диалоги не раздували каждый prompt бесконечно.

Текстовое описание агента лежит отдельно в Markdown-файле:

```text
server/agents/simple-agent.md
```

В этом же файле лежат дефолтные настройки агента: модель, temperature, язык, system prompt и демонстрационные лимиты контекста:

```text
max_context_tokens: 4000
reserved_output_tokens: 500
```

## Модель агента

Агент работает через DeepSeek Flash:

```text
MODEL_FLASH_NAME=deepseek-v4-flash
MODEL_FLASH_BASE_URL=https://api.deepseek.com
```

Вызов выполняется через OpenAI-compatible endpoint:

```text
POST https://api.deepseek.com/chat/completions
```

## Настройка

Создайте `.env` в корне проекта:

```bash
cp .env.example .env
```

Заполните ключ:

```bash
DEEPSEEK_API_KEY=your_deepseek_api_key_here
```

`DEFAULT_TASK` задает запрос, который появится в форме по умолчанию.

Параметры памяти агента можно переопределить через `.env`:

```bash
AGENT_MAX_CONTEXT_MESSAGES=40
AGENT_MAX_CONTEXT_CHARACTERS=24000
AGENT_CONTEXT_COMPRESSION_ENABLED=true
AGENT_CONTEXT_KEEP_LAST_MESSAGES=5
AGENT_CONTEXT_SUMMARY_BATCH_MESSAGES=5
MODEL_MAX_CONTEXT_TOKENS=4000
MODEL_RESERVED_OUTPUT_TOKENS=500
```

`AGENT_CONTEXT_KEEP_LAST_MESSAGES` задает N последних сообщений, которые агент подставляет в prompt как есть. Все более старые сообщения разбиваются на блоки по `AGENT_CONTEXT_SUMMARY_BATCH_MESSAGES` и заменяются summary. Summary хранится отдельно в JSON-файле чата рядом с полной историей, поэтому старые блоки не пересжимаются на каждом запросе.

`AGENT_MAX_CONTEXT_MESSAGES` и `AGENT_MAX_CONTEXT_CHARACTERS` остаются дополнительной защитой для точного хвоста истории. Значения выше всё ещё достаточно маленькие для демонстрации: короткий запрос проходит, длинный диалог показывает рост истории, а большое сообщение может превысить локальный budget. Если в `.env` уже указаны `MODEL_MAX_CONTEXT_TOKENS` или `MODEL_RESERVED_OUTPUT_TOKENS`, они переопределят настройки из файла агента.

Backend также считает токены для текущего запроса, выбранной истории, полной истории диалога и ответа модели. Если API возвращает `usage`, итоговые `input/output/total` берутся из API; если нет, используется локальная оценка. История для следующего вызова собирается как `summary старых блоков + последние N сообщений`, а одиночный запрос больше локального budget отклоняется до обращения к LLM.

После ответа UI показывает сравнение:

- `input без сжатия`: сколько токенов занял бы prompt с полной историей.
- `input со сжатием`: сколько токенов реально ушло в prompt после summary.
- `экономия`: разница в токенах и процентах.
- `summary`: количество использованных summary-блоков.
- `как есть`: сколько последних сообщений сохранено без изменений.

Качество без сжатия максимальное, пока полная история помещается в окно модели, но расход токенов растет на каждом ходе и в длинном диалоге приводит к переполнению. Качество со сжатием обычно немного хуже на дословных деталях старых сообщений, зато агент сохраняет факты, решения, ограничения и свежий хвост диалога, продолжает работать после роста истории и экономит input-токены.

В интерфейсе есть sidebar со списком чатов в стиле Codex. При старте frontend вызывает `GET /api/agent/chats`; если сохраненные чаты есть, они появляются в списке и выбранный чат загружает свою историю. Новый чат получает свой `sessionId` в URL, например:

```text
http://localhost:5173?sessionId=win-demo-1
```

Для каждого чата UI показывает отдельную статистику: сколько сообщений в истории, сколько токенов занимает история, общий лимит контекста, резерв на ответ, input-лимит, сколько input-токенов уже занято историей, сколько осталось для следующего запроса, сколько стоит повторная отправка истории и есть ли риск переполнения на следующем коротком запросе.

Для демонстрации роста токенов и стоимости также есть endpoint:

```text
GET /api/agent/token-demo
```

Он сравнивает короткий диалог, длинный диалог и диалог выше лимита модели. Основной UI оставлен простым, а endpoint можно использовать отдельно, чтобы показать, как каждый новый ход повторно отправляет историю, почему input-токены и стоимость растут, и что ломается при переполнении контекста.

Что показать при переполнении:

- Если отправить историю целиком, API модели может вернуть ошибку контекстного окна: запрос физически больше лимита модели.
- Если агент защищается и режет историю, старые факты исчезают из prompt: модель может забыть имя пользователя, ранние требования, ограничения задачи или принятые решения.
- Стоимость растет не только от нового сообщения: каждый следующий ход повторно оплачивает выбранную историю диалога.
- Слишком большой одиночный запрос ломается сразу: агент отклоняет его до вызова LLM и сообщает, на сколько токенов превышен лимит.

## Запуск в режиме разработки

```bash
npm run dev
```

Frontend будет доступен на `http://localhost:5173`.
Backend будет доступен на `http://localhost:3001`.

## Production-сборка

```bash
npm run build
npm start
```
