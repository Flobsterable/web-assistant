# Simple LLM Agent

Минимальное fullstack-приложение: React + TypeScript + Vite на frontend, Node.js + Express + TypeScript на backend.

## Что делает приложение

Пользователь вводит запрос в чат. Backend принимает сообщение, передает его отдельной сущности `SimpleAgent`, агент вызывает LLM через HTTP API и возвращает ответ в интерфейс.

Агент сохраняет историю каждого чата в отдельный JSON-файл внутри `server/data/agent-sessions/`, загружает ее при каждом запуске и отправляет прошлые сообщения выбранного чата в следующий LLM-вызов. Поэтому после перезапуска backend продолжает каждый диалог со своим контекстом.

## Явная модель памяти

Над памятью работает слой персонализации. Профиль пользователя явно задаёт имя, контекст (роль, опыт, сфера и цели), стиль ответа, формат и список постоянных ограничений. Выбранный `profileId` передаётся в каждом `POST /api/agent`, а сервер сам загружает профиль и добавляет его в защищённый system-контекст. Этот контекст применяется автоматически и не отключается вместе с долговременной памятью.

Профили хранятся в `server/data/profiles/<profileId>.json`. Долговременная память тоже изолирована по `profileId`, поэтому автоматически выученные предпочтения не смешиваются между людьми.

## Инварианты

Задавать инварианты необязательно: если список пуст, ассистент работает без этого слоя ограничений. Но каждый заданный и активный инвариант обязателен к применению. Инварианты хранятся отдельно от диалога и памяти, глобальны для ассистента, действуют во всех профилях и чатах и находятся в `server/data/invariants.json`. Поддерживаются четыре категории: архитектура, принятое техническое решение, ограничение стека и бизнес-правило. Их можно настроить в интерфейсе в разделе памяти, но переключатели рабочей и долговременной памяти на них не влияют.

Перед генерацией агент отдельным низкотемпературным вызовом проверяет запрос пользователя против всех активных инвариантов. Если найден конфликт, генерация решения не выполняется: агент сохраняет в историю контролируемый отказ, называет нарушенный инвариант, объясняет причину и предлагает искать совместимую альтернативу. После генерации выполняется вторая проверка уже подготовленного ответа; нарушающий ответ пользователю не показывается и заменяется таким же отказом. Неразбираемый результат проверки трактуется безопасно — как невозможность подтвердить совместимость.

Активные инварианты всегда добавляются в защищённый system-контекст с максимальным приоритетом и не удаляются механизмом сокращения памяти. Результат проверки доступен в `invariantCompliance`, в технических деталях ответа и в отдельном шаге `invariant_check` журнала хода.

API инвариантов:

```text
GET    /api/invariants
POST   /api/invariants
PUT    /api/invariants/:id
DELETE /api/invariants/:id
```

Пример правила:

```json
{
  "category": "stack-constraint",
  "title": "Только TypeScript",
  "rule": "В production-коде разрешён только TypeScript",
  "rationale": "Единый стек команды",
  "enabled": true
}
```

Память разделена физически и логически на три слоя:

| Слой | Что хранится | Область действия | Хранилище | Запись |
|---|---|---|---|---|
| Краткосрочная | сообщения текущего диалога | один чат | `server/data/agent-sessions/<sessionId>.json` | автоматически после успешного ответа |
| Рабочая | сжатое состояние всей задачи: цель, прогресс, ограничения, решения, артефакты и следующие шаги | одна задача/чат | `server/data/memory/working/<sessionId>.json` | пересобирается моделью после каждого успешного ответа; ручные записи сохраняются отдельно |
| Долговременная | профиль, решения, знания | профиль пользователя | `server/data/memory/long-term/default.json` | важные сведения профиля — автоматически; решения и знания — после подтверждения или явно через UI/API |

## Состояние долгоживущей задачи

Каждый ход дополнительно формализует состояние текущей задачи: обязательный этап, текущий шаг и ожидаемое действие. Этапы образуют конечный автомат `planning → execution → validation → done`: за один переход можно пройти только одно ребро, а после неуспешной проверки разрешён возврат из `validation` в `execution`. Переход `planning → execution` требует явного утверждения плана пользователем, а `validation → done` — успешной проверки. Запрос `execution → done` не превращается в два автоматических перехода: он отклоняется, состояние и данные текущего шага сохраняются, а причина доступна в `lastTransitionError`.

Текущий этап также добавляется как обязательный динамический инвариант перед генерацией и повторно проверяется на подготовленном ответе. Поэтому на запрещённую попытку ассистент объясняет допустимый следующий шаг вместо реализации или преждевременного финала. Пауза меняет только статус задачи и сессию, но не этап; после возобновления автомат продолжает работу с того же состояния.

Пауза не меняет этап задачи. Перед основным ответом отдельный классификатор определяет по смыслу сообщения и контексту диалога, хочет ли пользователь отложить текущую работу, вернуться к сохранённой задаче или просто продолжает обычный разговор. Он получает текущую рабочую память, последние реплики и список задач; фиксированные формулировки для управления задачами не требуются. Регулярные выражения используются только как аварийный fallback при недоступности классификатора.

При намерении отложить работу снимок рабочей памяти сохраняется в `server/data/tasks/<profileId>.json`. При намерении вернуться классификатор сопоставляет сообщение с задачами профиля, переводит выбранную задачу в активный режим и восстанавливает рабочую память текущего чата. Пользователю не нужно повторно объяснять контекст. Сохранённые задачи и их состояние также показаны в интерфейсе.

API задач:

```text
GET    /api/tasks?profileId=<id>
POST   /api/tasks/:id/resume
DELETE /api/tasks/:id?profileId=<id>
```

Перед каждым вызовом модели агент собирает prompt в порядке приоритета: system prompt, долговременная память, рабочее сжатие задачи, свежий хвост диалога, затем текущий запрос. В отчёте ответа `contextManagement.memory` видно количество элементов, токены и ID записей, которые действительно попали в prompt. Если окно контекста мало, свежий диалог и основная цель/ограничения рабочей памяти имеют приоритет над долговременной.

После завершения каждого хода отдельный LLM-вызов получает предыдущее рабочее сжатие, свежую историю и новую пару `user/assistant`. Он возвращает строгий JSON с обновлённым состоянием всей задачи и кандидатами в долговременную память. Поэтому working не является копией последних сообщений: старые договорённости остаются в сжатии, пока актуальны, а устаревшие удаляются моделью.

Кандидаты long-term извлекаются из запросов пользователя во всём доступном окне с учётом рабочего сжатия и уже накопленного профиля. Агент формирует короткую выжимку, а не копирует последнюю реплику. Устойчивые и важные сведения категории `profile` (язык, роль, стиль ответа, предпочтения и постоянные ограничения пользователя) сохраняются автоматически в стабильные профильные ключи; повторный сигнал обновляет существующую выжимку вместо создания дубликата. Решения и знания попадают в `pending`, где ждут подтверждения. Низкая уверенность не меняет память, `update/delete` требуют существующий `targetId`, а автоматическое удаление запрещено. Порог уверенности задаётся через `MEMORY_CONFIDENCE_THRESHOLD` (по умолчанию `0.75`), порог автоматического сохранения профиля — через `MEMORY_PROFILE_AUTO_SAVE_THRESHOLD` (по умолчанию `0.7`). Долговременная память хранится в общем `memory/long-term/default.json` и добавляется в контекст любого диалога.

В UI есть независимые переключатели рабочей и долговременной памяти. Они управляют только использованием слоя в ответе: выключенный слой не попадает в prompt, но его данные не удаляются. Рабочее сжатие продолжает обновляться после хода, поэтому можно сравнивать ответы с памятью и без неё, не теряя накопленный контекст. Выбор переключателей сохраняется в браузере.

Значения памяти передаются модели как экранированные данные внутри `<memory_data>`, поэтому сохранённый текст не может закрыть блок и подменить system prompt. При нехватке контекста сначала отбрасывается long-term, затем менее важный working и старая история; цель и ограничения working получают приоритет.

API памяти:

```text
GET    /api/agent/memory?sessionId=<id>
POST   /api/agent/memory
DELETE /api/agent/memory/:layer/:id?sessionId=<id>
GET    /api/agent/memory/pending?sessionId=<id>
POST   /api/agent/memory/pending/:id/approve
POST   /api/agent/memory/pending/:id/reject
```

API профилей:

```text
GET    /api/profiles
POST   /api/profiles
PUT    /api/profiles/:id
DELETE /api/profiles/:id
```

Каждый запрос получает `turnId`. Структурированные шаги `memory_load`, `memory_classification`, `memory_policy`, `context_assembly`, `provider_request`, `conversation_persist` и `memory_persist` сохраняются отдельно от истории в `server/data/agent-logs/<sessionId>/<turnId>.json`.

```text
GET /api/agent/logs?sessionId=<id>
GET /api/agent/logs/:turnId?sessionId=<id>
```

Пример явной записи:

```json
{
  "sessionId": "win-demo",
  "layer": "working",
  "category": "constraint",
  "key": "response_format",
  "value": "Отвечать коротким списком"
}
```

Для проверки изоляции слоёв и их влияния на prompt выполните `npm test`. Интеграционные тесты также создают два контрастных профиля, проверяют разные system-prompt и подтверждают, что профиль применяется даже при выключенной long-term памяти.

Главное требование выполнено: логика запроса, ответа и восстановления контекста инкапсулирована в агенте, а endpoint `/api/agent` только валидирует входные данные, создает агента и запускает его.

Хранилище использует атомарную запись через временный файл, хранит завершенные пары `user`/`assistant` и формирует ограниченное контекстное окно из памяти и свежей истории, чтобы старые диалоги не раздували каждый prompt бесконечно.

Текстовое описание агента лежит отдельно в Markdown-файле:

```text
server/agents/simple-agent.md
```

В этом же файле лежат дефолтные настройки агента: модель, temperature, язык, system prompt и демонстрационные лимиты контекста:

```text
max_context_tokens: 40000
reserved_output_tokens: 500
```

## Модель агента

Агент работает через DeepSeek Flash:

```text
MODEL_FLASH_NAME=deepseek-v4-flash
MODEL_FLASH_BASE_URL=https://api.deepseek.com
```

Вызов выполняется через OpenAI-compatible endpoint:

```text
POST https://api.deepseek.com/chat/completions
```

Перед отправкой сообщения модель можно выбрать в интерфейсе. Список формируется на сервере только из настроенных моделей (`MODEL_GEMINI`, `MODEL_FLASH`, `MODEL_PRO`), а выбранный ID проверяется endpoint-ом `/api/agent`. Выбор сохраняется в браузере и используется как для основного ответа, так и для обновления памяти после хода.

## Настройка

Создайте `.env` в корне проекта:

```bash
cp .env.example .env
```

Заполните ключ:

```bash
DEEPSEEK_API_KEY=your_deepseek_api_key_here
```

Параметры памяти агента можно переопределить через `.env`:

```bash
AGENT_MAX_CONTEXT_MESSAGES=40
AGENT_MAX_CONTEXT_CHARACTERS=24000
AGENT_CONTEXT_KEEP_LAST_MESSAGES=5
MODEL_MAX_CONTEXT_TOKENS=40000
MODEL_RESERVED_OUTPUT_TOKENS=500
```

`AGENT_CONTEXT_KEEP_LAST_MESSAGES` задает N последних сообщений, которые агент подставляет в prompt как есть. Отдельного пользовательского выбора режима контекста нет: агент всегда использует единый порядок `system → long-term → working → свежая история → текущий запрос`.

`AGENT_MAX_CONTEXT_MESSAGES` и `AGENT_MAX_CONTEXT_CHARACTERS` остаются дополнительной защитой для точного хвоста истории. Значения выше всё ещё достаточно маленькие для демонстрации: короткий запрос проходит, длинный диалог показывает рост истории, а большое сообщение может превысить локальный budget. Если в `.env` уже указаны `MODEL_MAX_CONTEXT_TOKENS` или `MODEL_RESERVED_OUTPUT_TOKENS`, они переопределят настройки из файла агента.

Backend также считает токены для текущего запроса, выбранной истории, полной истории диалога и ответа модели. Если API возвращает `usage`, итоговые `input/output/total` берутся из API; если нет, используется локальная оценка. История для следующего вызова собирается из памяти и последних N сообщений, а одиночный запрос больше локального budget отклоняется до обращения к LLM.

После ответа UI показывает сравнение:

- `input без управления`: сколько токенов занял бы prompt с полной историей.
- `managed input`: сколько токенов реально вошло в управляемый prompt.
- `экономия`: разница в токенах и процентах.
- `как есть`: сколько последних сообщений сохранено без изменений.

В интерфейсе есть sidebar со списком чатов в стиле Codex. При старте frontend вызывает `GET /api/agent/chats`; если сохраненные чаты есть, они появляются в списке и выбранный чат загружает свою историю. Новый чат получает свой `sessionId` в URL, например:

```text
http://localhost:5173?sessionId=win-demo-1
```

Для каждого чата UI показывает отдельную статистику: сколько сообщений в истории, сколько токенов занимает история, общий лимит контекста, резерв на ответ, input-лимит, сколько input-токенов уже занято историей, сколько осталось для следующего запроса, сколько стоит повторная отправка истории и есть ли риск переполнения на следующем коротком запросе.

Для демонстрации роста токенов и стоимости также есть endpoint:

```text
GET /api/agent/token-demo
```

Он сравнивает короткий диалог, длинный диалог и диалог выше лимита модели. Основной UI оставлен простым, а endpoint можно использовать отдельно, чтобы показать, как каждый новый ход повторно отправляет историю, почему input-токены и стоимость растут, и что ломается при переполнении контекста.

Что показать при переполнении:

- Если отправить историю целиком, API модели может вернуть ошибку контекстного окна: запрос физически больше лимита модели.
- Если агент защищается и режет историю, старые факты исчезают из prompt: модель может забыть имя пользователя, ранние требования, ограничения задачи или принятые решения.
- Стоимость растет не только от нового сообщения: каждый следующий ход повторно оплачивает выбранную историю диалога.
- Слишком большой одиночный запрос ломается сразу: агент отклоняет его до вызова LLM и сообщает, на сколько токенов превышен лимит.

## MCP connections

В приложение встроен MCP-сервер `Google Calendar` со Streamable HTTP-подобным
JSON-RPC endpoint:

```text
POST http://localhost:3001/mcp/google-calendar
```

Он регистрирует инструменты `google_calendar_list_events`,
`google_calendar_create_event` и `google_calendar_delete_event`, публикует их
через `tools/list` и выполняет через `tools/call`. Они возвращают события за
период, создают встречи и удаляют событие по точному `eventId`.

Агент подключён к этому endpoint как MCP-клиент. Перед основным ответом модель
решает, нужен ли календарь, затем клиент выполняет последовательность
`initialize → notifications/initialized → tools/list → tools/call`. Результат
возвращается модели в отдельном защищённом блоке данных. Фактический вызов виден
в `Технические детали → MCP` под ответом агента.

### Настройка Google OAuth

1. В [Google Cloud Console](https://console.cloud.google.com/) создайте проект и
   включите Google Calendar API.
2. Настройте OAuth consent screen. Для тестового External-приложения добавьте
   свой Google-аккаунт в Test users.
3. Создайте OAuth Client ID типа **Web application**.
4. Добавьте Authorized redirect URI:

   ```text
   http://localhost:3001/api/google-calendar/oauth/callback
   ```

5. Заполните `.env`:

   ```text
   GOOGLE_CALENDAR_CLIENT_ID=...
   GOOGLE_CALENDAR_CLIENT_SECRET=...
   GOOGLE_CALENDAR_REDIRECT_URI=http://localhost:3001/api/google-calendar/oauth/callback
   ```

6. Перезапустите `npm run dev`, откройте `Расширения → MCP` и нажмите
   `Войти через Google`.

Запрашивается scope `calendar.events`: сервер читает расписание и создаёт
встречи, но не получает доступ к настройкам аккаунта. После обновления с версии,
которая использовала `calendar.readonly`, календарь нужно отключить и подключить
снова. OAuth token хранится в
`server/data/secrets/google-calendar-token.json` с правами `0600`; весь каталог
`server/data` исключён из Git. Кнопка отключения отзывает token в Google и
удаляет локальный файл.

Проверка в чате:

```text
Какие встречи у меня в календаре на ближайшие 7 дней?
```

Если аккаунт не подключён, MCP всё равно вернёт корректный tool result с
`isError: true`, а агент предложит пройти OAuth.

Экран также подключает произвольные публичные Streamable HTTP MCP endpoints
через официальный SDK `@modelcontextprotocol/client`. Для таких внешних
подключений пока выполняются только `initialize` и `tools/list`.

После успешного discovery имя, версия, endpoint и список tools сохраняются в
`server/data/mcp-connections.json`. Значение авторизационного header не сохраняется.
Нажатие на карточку сервиса открывает его инструменты; кнопка `Удалить MCP`
удаляет подключение из реестра.

## Планировщики и фоновые сводки

В приложение встроен второй MCP-сервер:

```text
POST http://localhost:3001/mcp/planner
```

Он сохраняет списки дел и готовые сводки в SQLite-файле
`server/data/planner.sqlite`. Данные изолированы по `profileId`. Один вызов
`planner_save_todos` может сохранить до 50 отдельных пунктов списка.
Сообщения о результате обрабатываются отдельно: например, «я забрал заказ на
Ozon» вызывает `planner_complete_todos`, находит похожее незавершённое дело и
отмечает его выполненным. Совпадение должно быть достаточно точным: заказ в
Ozon не закроет активное дело про Хобби Геймс. Если подходящего дела нет или
совпадение неоднозначно, сервер без уточняющего вопроса создаёт отдельную
выполненную запись — она попадёт в дневную и недельную сводки.

По явной команде `planner_delete_todos` удаляет выбранные дела по смысловому
названию или очищает весь список (`all=true`). `planner_delete_summaries`
удаляет дневную, недельную либо обе сохранённые сводки. Эти инструменты помечены
как destructive. Удалённая сводка будет создана заново при следующем запуске
фонового worker.

Отдельный экран `Расширения → Планировщики` показывает:

- сохранённый через MCP список дел;
- краткую сводку за день, открываемую по нажатию;
- краткую сводку за неделю, открываемую по нажатию.

В тестовом режиме фоновый worker пересобирает дневную сводку раз в минуту, а
недельную — раз в две минуты. В отчёт входят выполненные и добавленные дела,
оставшаяся работа, просрочки и встречи Google Calendar за соответствующий
календарный период. Если календарь временно недоступен, сводка по делам всё равно
создаётся, а ошибка интеграции видна в состоянии scheduler. Первый набор сводок
создаётся при запуске backend, затем экран автоматически получает обновления.

Для запроса о новой встрече MCP-orchestrator выполняет длинный межсерверный flow:

```text
google-calendar/tools/list + planner/tools/list
→ google_calendar_create_event
→ planner_save_todos (dueAt = event.start, ссылка и event.id в description)
→ итоговый ответ агента
```

Обычное дело без времени встречи маршрутизируется только в Planner. Если запись
в календарь завершилась ошибкой, зависимое дело не создаётся, поэтому агент не
сообщает о несуществующей встрече.

Удаление встречи выполняется безопасной цепочкой:

```text
google_calendar_list_events
→ google_calendar_delete_event (точный event.id)
→ planner_list_todos
→ planner_delete_todos (точный todo.id связанного дела)
```

Если поиск календаря неоднозначен, удаление не выполняется: агент просит
уточнить встречу. После успешного удаления события удаляется только дело, в
описании которого сохранён тот же `event.id`; одноимённые дела не затрагиваются.

Дневная сводка охватывает текущий календарный день в часовом поясе
`PLANNER_TIMEZONE` (по умолчанию `Asia/Omsk`). Будущие сроки показываются как
результат сегодняшнего планирования: например, «на вторник запланировано …», а
не как дело на сегодня. Недельная сводка охватывает текущую календарную неделю
с понедельника по текущий момент.

Тот же `PLANNER_TIMEZONE` используется при разборе времени встречи без явно
указанного пояса. Например, `14:00` при `Asia/Omsk` передаётся календарю как
`14:00:00+06:00`, а не `14:00:00Z`. Границы запросов событий для дневной и
недельной сводки также вычисляются по местным суткам, после чего переводятся в
UTC для Google Calendar API.

Каждый календарный event с `event.id`, найденный фоновым worker, идемпотентно
синхронизируется в список дел. В `description` хранится ключ
`Google Calendar event: <event.id>`, поэтому повторные дневные и недельные
запуски не создают дубликаты. Такая встреча одновременно отображается как дело,
как календарное событие в сводке и в разделе Google Calendar Markdown-отчёта.
Для списка дел worker отдельно синхронизирует предстоящие 90 дней, поэтому
встреча следующей недели или месяца появляется до начала соответствующего периода.

Примеры запросов в чат:

```text
Мои дела: подготовить отчёт, позвонить клиенту, купить продукты.
Покажи мои незавершённые дела.
Отметь подготовку отчёта выполненной.
Очисти список дел.
Удали недельную сводку.
Покажи сводки за день и за неделю.
```

### Композиция MCP-инструментов: отчёт по задачам

Агент поддерживает не только одиночный вызов, но и автоматическую цепочку MCP-инструментов. Например, запрос:

```text
Составь отчёт по моим незавершённым задачам и сохрани его.
```

запускает последовательность:

```text
planner_list_todos
  → google_calendar_list_events
  → planner_build_report
  → planner_validate_report
  → planner_save_report
```

`planner_list_todos` получает дела, а `google_calendar_list_events` — встречи за
тот же дневной или недельный период. `planner_build_report` принимает массивы
`todos` и `calendarEvents`, формирует единый Markdown со статистикой, встречами,
просроченными и приоритетными задачами и возвращает короткий `reportId`.
`planner_validate_report` принимает этот ID, проверяет неизменённый серверный
черновик и возвращает `validationId`. Только этот ID принимает
`planner_save_report`. Поэтому модель не переносит большой Markdown между
вызовами и не может случайно изменить контрольные данные отчёта.

Файлы сохраняются в изолированные по профилям каталоги:

```text
server/data/reports/<profileId>/
```

Если имя уже занято, инструмент создаёт новый файл с числовым суффиксом и не
перезаписывает существующий отчёт. После успешного сохранения полный Markdown
автоматически добавляется в ответ агента, поэтому содержимое сразу видно в чате
вместе с путём к файлу. Все фактические вызовы цепочки отображаются в
`Технические детали → MCP`.

Цикл MCP ограничен шестью вызовами на один запрос и прекращается при ошибке или
попытке повторить тот же инструмент с теми же аргументами. Это защищает агента
от зацикливания и повторных операций записи.
